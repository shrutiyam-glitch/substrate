	// Graceful shutdown knobs. atelet is dialed directly by pod IP (not via a
	// Service), so ateapi does not gate on pod readiness and no route-drain
	// window is needed; drain-delay therefore defaults to 0. drain-timeout is
	// long by default because Checkpoint/Restore stream multi-GiB snapshots to
	// object storage and can take minutes — force-cancelling one mid-upload
	// crashes the actor. The sum drain-delay+drain-timeout must fit within the
	// pod's terminationGracePeriodSeconds, or the kubelet SIGKILLs first.


// drainOnShutdown drives graceful shutdown when ctx is cancelled (SIGTERM or
// interrupt): it marks the process not-ready, waits drain-delay while still
// accepting work, then GracefulStop()s the gRPC server so in-flight RPCs finish.
// If they run past drain-timeout it forcefully Stop()s. The returned channel
// closes once shutdown completes, so main can block on it before exiting (and
// letting the deferred tracer/meter flushes run). Mirrors ateapi's
// drainOnShutdown.

Testing - 

  Reframe: the axis is "what is atelet doing when SIGTERM lands," not "what state is the actor in"

  atelet is a node supervisor — it doesn't hold actor state. Its termination behavior depends entirely on which of its RPCs (Run / Checkpoint / Restore) is in-flight at the 
  instant SIGTERM arrives, and how far along it is. The actor's state is just the context that determines whether an RPC is in-flight. So "actor is SUSPENDED" isn't really an
  atelet-termination case — a SUSPENDED actor has no worker/node binding, so atelet is doing nothing for it (that's the idle case).

  So the right question per case is: is there an in-flight RPC, which one, and what happens if it's (a) allowed to finish vs (b) force-cancelled at the timeout?

  Cases you didn't list but should include:
  - #6 concurrency — atelet serves all actors on its node; a real node drain can have several checkpoints in flight at once, sharing one timeout budget.
  - #7 new-RPC-during-drain — proves atelet stops accepting correctly (the "stop accepting new RPCs" half of the issue).
  - Grace-period exceeded (misconfig) — if drain-delay + drain-timeout > terminationGracePeriodSeconds, the kubelet SIGKILLs first and the drain is truncated. This is a
  config-correctness case (why we set grace=330 ≥ 0+5m).
  - Non-SIGTERM death (OOM/segfault) — bypasses the drain entirely. Out of #719's scope, but a real operational scenario worth knowing the drain does not cover.

  A secondary dimension cutting across #2–#5: snapshot scope (FULL vs DATA) and workload size determine how long the RPC takes, which decides whether force-stop even triggers.
  That's exactly what bit us on kind — the tiny counter's checkpoint was sub-second (and here, broken), so there was no window.

  Coverage today: case #1 was proven live; #2's force-stop is proven by the unit test. #3–#7 are the same drainOnShutdown mechanism with different in-flight RPCs, so the unit
  test's two paths (finish-within vs force-after-timeout) generalize — but if you want belt-and-suspenders, the Restore/Run cases (#4/#5) are the safe ones to exercise live
  because their abort is recoverable.
